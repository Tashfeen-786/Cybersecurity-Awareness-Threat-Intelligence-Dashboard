# Database Design (SQLite)

Database file: `backend/threat_intel.db` (regenerated by
`scripts/init_database.py` / `python -m scripts.init_database`).
Connections enable `PRAGMA foreign_keys = ON` and WAL mode. All queries are
parameterized.

## Tables and required columns (per the project brief)

| Table | Purpose | Key columns |
|---|---|---|
| THREATS | normalized threat records | threat_id, threat_name, category, description, severity, risk_score, confidence_score, status, first_seen, last_seen |
| INDICATORS | one validated indicator row per threat | indicator_id, threat_id (FK), indicator_type, indicator_value, first_seen, last_seen |
| SOURCES | intelligence sources + reliability grade | source_id, source_name, reliability (A-D) |
| ATTACK_MAPPINGS | justified ATT&CK mappings | mapping_id, threat_id (FK), tactic, technique, technique_id (optional) |
| VULNERABILITIES | synthetic CVEs + contextual priority | vulnerability_id, cve_id, severity, cvss_score, patch_available, priority_score |
| ALERTS | SOC alert queue | alert_id, threat_id (FK), severity, risk_score, status, created_at |
| ANALYST_NOTES | protected investigation notes | note_id, threat_id (FK), note, created_at |
| AWARENESS_MODULES | learning modules served to the UI | module_id, title, category |
| QUIZ_RESULTS | anonymous quiz history (awareness trend) | result_id, anonymous_user_id, overall_score, created_at |

**Documented extensions** (required by other brief sections):
`TIMELINE_EVENTS` (per-threat investigation timeline), `AUDIT_LOG`
(administrative changes are auditable), `META` (dataset provenance).

## Relationships

* SOURCES 1—N THREATS (`threats.source_id → sources.source_id`)
* THREATS 1—N INDICATORS, ATTACK_MAPPINGS, ANALYST_NOTES, TIMELINE_EVENTS,
  ALERTS (all with `ON DELETE CASCADE`)
* VULNERABILITIES ↔ THREATS linked logically via `threats.cve_id`
* AWARENESS_MODULES and QUIZ_RESULTS are standalone (awareness track)

## Indexes

```sql
idx_threats_severity, idx_threats_category, idx_threats_status,
idx_threats_risk (DESC), idx_threats_confidence (DESC),
idx_threats_indicator, idx_threats_campaign, idx_threats_last_seen (DESC),
idx_indicators_value, idx_indicators_threat,
idx_attack_threat, idx_attack_tactic, idx_attack_tech,
idx_vuln_severity, idx_vuln_priority (DESC), idx_vuln_cve,
idx_alerts_status, idx_alerts_threat, idx_alerts_severity,
idx_notes_threat, idx_timeline_threat
```

These indexes back the dashboard aggregations, the IOC search lookups
(`indicators.indicator_value`), the filter/sort queries and the alert queue.

## Why the notes need protection

`ANALYST_NOTES` contain investigation findings; they are masked in API
responses unless the caller presents a valid API key (see
docs/security_privacy.md — threat-intelligence data itself requires access
control because it reveals defensive posture).

## PostgreSQL migration note

The schema uses portable SQL types. For PostgreSQL: replace
`AUTOINCREMENT` with `GENERATED ALWAYS AS IDENTITY`, keep the same indexes,
and point `DATABASE_PATH` at a DSN via SQLAlchemy — the service layer is
already isolated behind parameterized queries.
